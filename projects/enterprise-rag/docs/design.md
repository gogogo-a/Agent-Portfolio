# 企业 RAG · 详细设计

## 思想

1. **先分流再检索**：FAQ 能答就不要进重检索。  
2. **检索质量要可判定**：不是 top_k 一扔给 LLM；中间有质量判断与改写回环。  
3. **切分决定上限**：embedding 只有 512 token 时，入库前必须可控切块。  
4. **用评测驱动改节点**：失败要落到具体节点（路由 / chunk / 作答）。

## 主流程

```text
开始
 → 意图识别1(FAQ) → 解析JSON → FAQ命中?
      ├─ 是 → 写 final_reply → 结束
      └─ 否 → 意图识别2(选库+改写+实体)
             → 生成循环列表
             → Iteration: 检索 → 质量判断 → 合并 useful_chunks
             → 依据 chunk 回复 → 结束
```

## 模型参数约定（可公开）

| 节点 | temperature | 强制 JSON | 记忆 |
|------|-------------|-----------|------|
| FAQ / 意图2 / 质量判断 | 0 | 开 | FAQ 关；其余按需短记忆 |
| 依据 chunk 作答 | 偏创作可略高 | 关 | 可开 |

## 混合检索与图谱（面试口径 · 学习/实践总结）

- **向量**：如 bge 类模型，余弦相似度；召回量受 rerank 耗时约束  
- **关键词 / BM25**：稳住专有名词，减少「飘库」  
- **图谱**：解决「实体关系约束」缺失导致的多主体混淆（公司-系统-技术文档）  
- **顺序**：先判断是否强关系问题 → 图检索 + 质量判定 → 不足再混合检索 → 融合作答

> 说明：不同客户环境组件不全相同；作品集以「高铁知识检索」落地流程为主，图谱/混合检索为可迁移设计思想。

## 语义分块（方案 B）摘要

1. 按句缝切开（。！？；与换行）  
2. 每个缝取左右窗 embedding，算 cosine  
3. 本批相似度 **P20** 作自适应阈值 τ，结合邻域中位数标候选切点  
4. 长度门闩：太短不切、接近目标触发语义切、接近硬顶强制切  
5. 插入 `\n##\n` 后再交平台按分隔符入库
